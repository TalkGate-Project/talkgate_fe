# 웹 접근성(Web Accessibility) 맥락 가이드

다른 팀에서 접근성을 중요하게 다룰 때 대화할 수 있도록, **무엇인지·왜 중요한지·어떤 영역이 있는지·어떻게 배우는지** 맥락을 잡기 위한 문서입니다.  
지금 당장 구현을 하겠다는 전제가 아니라, "접근성이란 무엇이고 어떻게 접근하면 되는지"를 정리한 것입니다.

---

## 1. 접근성이란 무엇인가

**웹 접근성(Web Accessibility)** 은 **장애가 있든 없든, 나이·환경이 어떻든, 모든 사용자가 웹 콘텐츠를 인지하고, 조작하고, 이해할 수 있도록 만드는 것**입니다.

- **시각**: 시력 저하, 색맹, 저시력, 실명(스크린 리더 사용)
- **운동/신체**: 마우스 사용 어려움 → 키보드만 사용, 스위치 등 보조 기기
- **청각**: 영상/오디오에 대체 텍스트(자막, 전사)
- **인지**: 읽기/집중 어려움 → 단순한 문장, 예측 가능한 구조, 충분한 시간

"일부 사용자만의 이야기"가 아니라, **키보드만 쓰는 사람, 터치만 쓰는 사람, 작은 화면·저사양 환경**까지 포함한 **사용성의 확장**으로 보는 게 좋습니다.

---

## 2. 왜 중요한가 (팀/조직 관점)

- **법·규제**: 한국은 「국가정보화기본법」, 「장애인차별금지법」 등에 따라 공공·일부 서비스는 접근성 준수 의무가 있음. 해외는 ADA(미국), EAA(유럽) 등.
- **사용자 폭**: 장애인 비율은 인구의 상당 부분이고, 일시적 불편(손 부상, 조명 불량)까지 포함하면 “접근성 필요 사용자”는 더 많음.
- **다른 팀과의 협업**: 디자인·QA·정책팀이 “WCAG 2.1 AA 기준으로 검수한다”처럼 말할 수 있음. 이때 기준과 용어를 알아두면 소통이 수월함.

그래서 “당장 우리 서비스에 강제가 없어도” **개념과 용어, 대략적인 수준**만 알아두면 다른 팀과 이야기할 때 유리합니다.

---

## 3. 기준: WCAG (Web Content Accessibility Guidelines)

가장 널리 쓰이는 표준은 **W3C WCAG**입니다.

- **WCAG 2.1** (현재 많이 참조), **WCAG 2.2** (최신, 2.1 확장)
- **레벨**
  - **A**: 최소한의 접근성 (미충족 시 심각한 장벽)
  - **AA**: 대부분의 정책·계약에서 요구하는 수준 (목표로 삼는 경우가 많음)
  - **AAA**: 더 높은 수준 (필수보다는 “가능하면” 수준)

다른 팀이 “WCAG 2.1 AA 기준으로 맞춰주세요”라고 하면, **W3C WCAG 2.1 문서에서 “Level AA” 성공 기준**을 의미한다고 보면 됩니다.

- 공식 문서: [WCAG 2.1](https://www.w3.org/TR/WCAG21/)  
- 한글 요약/체크리스트를 검색해 보면 “WCAG 2.1 AA 체크리스트” 형태로 정리된 자료가 많습니다.

---

## 4. 어떤 영역이 있는지 (큰 그림)

접근성을 **주제별**로 나누면 대략 아래와 같습니다. “키보드만으로 모든 동작”은 이 중 **2번(키보드)·3번(포커스)·4번(시맨틱/ARIA)** 과 많이 연결됩니다.

### 4.1 인지 가능 (Perceivable)

- **대체 텍스트**: 이미지에 `alt`, 아이콘 버튼에 `aria-label` 등. “무엇인지”를 텍스트로 제공.
- **색에만 의존하지 않기**: “빨간색 = 오류”만 쓰지 말고, 아이콘이나 문구로도 구분.
- **명암 대비**: 글자와 배경의 대비 비율(Contrast Ratio). WCAG AA는 일반 텍스트 4.5:1, 큰 글씨 3:1 등.
- **자막/전사**: 영상·오디오에 자막 또는 텍스트 대안.

### 4.2 조작 가능 (Operable)

- **키보드만으로 모든 기능 사용**: 포커스 가능하게 하고, Tab/Enter/Space로 조작 가능해야 함.
- **충분한 시간**: 자동으로 사라지는 콘텐츠는 연장/정지 옵션.
- **깜빡임/발작 유발 콘텐츠 주의**: 일부 플래시는 발작 위험이 있어 제한.
- **네비게이션**: 건너뛰기 링크, 제목 구조(`h1`~`h6`)로 “어디가 어디인지” 파악 가능하게.

### 4.3 이해 가능 (Understandable)

- **읽기 쉬운 문장**: 약어 설명, 일관된 용어.
- **예측 가능한 동작**: 링크/버튼이 클릭 시 무엇이 일어날지 예측 가능하게.
- **입력 오류 안내**: 폼 오류 시 무엇이 잘못되었는지, 어떻게 고치면 되는지 명확히.

### 4.4 견고함 (Robust)

- **마크업/API가 보조 기술과 호환**: HTML 시맨틱을 지키고, ARIA를 올바르게 쓰면 스크린 리더 등이 해석하기 좋음.

이 네 가지는 WCAG의 **POUR 원칙**(Perceivable, Operable, Understandable, Robust)에 대응합니다.

## 5. 프론트엔드에서 자주 나오는 주제 (실무 맥락)

다른 프론트엔드 팀과 얘기할 때 자주 나오는 것들만 추리면:

| 주제 | 의미 | 예시 |
|------|------|------|
| **키보드 접근성** | 마우스 없이 키보드만으로 모든 동작 가능 | Tab으로 포커스 이동, Enter/Space로 버튼 활성화, Esc로 모달 닫기 |
| **포커스 관리** | 포커스가 “보이는 곳”과 “실제 포커스”가 맞고, 논리적인 순서로 이동 | 모달 열릴 때 포커스를 모달 안으로, 닫을 때 열기 버튼으로 복귀 |
| **포커스 가시성** | 현재 포커스된 요소를 시각적으로 구분 | `:focus-visible` 또는 `outline`으로 포커스 링 표시 |
| **시맨틱 HTML** | 역할에 맞는 태그 사용 | 버튼은 `<button>`, 내비는 `<nav>`, 제목은 `<h1>`~`<h6>` |
| **ARIA** | 보조 기술용 추가 정보. “HTML만으로 역할/상태를 표현하기 어려울 때” 보조 | `aria-label`, `aria-expanded`, `role="dialog"`, `aria-live` 등 |
| **스크린 리더** | 화면을 읽어주는 소프트웨어. 시맨틱·ARIA·텍스트 순서에 의존 | “버튼, 메뉴”, “대화상자 열림” 같은 안내가 나오도록 구조화 |
| **대비** | 글자와 배경의 명암 비율 | 디자인 단계에서 4.5:1(일반 텍스트) 등 확인 |

“키보드만으로 모든 동작”을 하려면 **키보드 접근성 + 포커스 관리 + 시맨틱/ARIA**를 같이 봐야 합니다.

## 6. 어떻게 공부하면 좋은지

### 6.1 순서 추천 (맥락 잡기용)

1. **WCAG가 무엇인지, A/AA/AAA가 무슨 의미인지**  
   → 공식 사이트 한 번 훑어보기 + “WCAG 2.1 AA 체크리스트” 한글 자료 하나 골라 읽기.

2. **시맨틱 HTML**  
   → `<button>` vs `<div onClick>`, `<nav>`, `<main>`, 제목 계층. “의미에 맞는 태그”가 접근성의 기반임을 이해.

3. **키보드만으로 사용해 보기**  
   → 자신이 만든 페이지에서 마우스를 놓고 Tab/Enter/Space만으로 한 번 돌아다녀 보기. 어디서 막히는지가 곧 개선 포인트.

4. **포커스와 ARIA 기초**  
   → `:focus` / `:focus-visible`, 모달 열릴 때 포커스 트랩/복귀.  
   → `aria-label`, `aria-expanded`, `role="button"` 등 “언제 무엇을 쓰는지” 위주로.

5. **스크린 리더 체험**  
   → Windows: NVDA(무료), macOS: VoiceOver 내장.  
   → 자주 쓰는 페이지 한두 개를 스크린 리더로만 사용해 보면 “무엇이 읽히고 무엇이 안 읽히는지” 감이 옴.

6. **자동 검사 도구**  
   → Lighthouse 접근성 탭, axe DevTools 등.  
   → “도구가 잡아주는 것”과 “직접 키보드/스크린 리더로 확인하는 것” 둘 다 필요하다고 보면 됨.

### 6.2 참고 자료 (시작용)

- **W3C WAI (Web Accessibility Initiative)**  
  - [Introduction to Web Accessibility](https://www.w3.org/WAI/fundamentals/accessibility-intro/)  
  - [WCAG Quick Reference](https://www.w3.org/WAI/WCAG21/quickref/)

- **MDN Accessibility**  
  - [Accessibility - MDN](https://developer.mozilla.org/en-US/docs/Web/Accessibility)  
  - 시맨틱, ARIA, 키보드 등 개발자 관점 정리.

- **WebAIM**  
  - [WebAIM](https://webaim.org/)  
  - 가이드, 체크리스트, 요약 문서가 많음.

- **한국형 웹 콘텐츠 접근성 지침(KWCAG)**  
  - 국내 공공·정책 논의 시 자주 언급됨. WCAG와 대응 관계만 알아두어도 도움됨.

- **도구**  
  - Lighthouse (Chrome DevTools)  
  - axe DevTools (브라우저 확장)  
  - Contrast checker (색 대비 확인)

## 7. “접근성 전면 개선”이 부담스러울 때

- **전면 개선** = 키보드만으로 모든 동작 + 스크린 리더 완벽 대응 + 대비·시간 등 WCAG AA 전 항목을 한 번에 맞추는 것.  
  → 작업량이 크고, 팀에 경험이 없으면 부담이 큼.

- **우선 할 수 있는 것**  
  - 새로 만드는 UI: 버튼은 `<button>`, 포커스 가능·가시성 확인.  
  - 중요한 버튼/아이콘에 `aria-label` 추가.  
  - 모달/드롭다운: 열릴 때 포커스 이동, 닫을 때 복귀.  
  - 디자인 리뷰 단계에서 “색만으로 구분하지 말 것, 대비 확인”을 한 번씩 언급.

이 정도만 해도 “접근성을 모르는 상태”에서 “맥락을 아는 상태”로 올라가고, 다른 팀이 “접근성 중요하다”고 할 때 **무슨 기준(WCAG, A/AA)을 말하는지, 키보드/ARIA/대비가 왜 나오는지** 대화할 수 있습니다.

---

## 8. 한 줄 요약

- **접근성** = 모든 사용자가 콘텐츠를 인지·조작·이해할 수 있게 하는 것.  
- **표준** = WCAG 2.1 (레벨 A/AA/AAA).  
- **실무에서 자주 나오는 것** = 키보드 사용, 포커스, 시맨틱 HTML, ARIA, 색 대비.  
- **공부 순서** = WCAG/체크리스트 → 시맨틱 HTML → 키보드로 직접 사용해 보기 → 포커스/ARIA → 스크린 리더 체험 → 도구 활용.  
- **당장 전면 개선이 어렵다면** = 새 UI부터 시맨틱·포커스·aria-label을 조금씩 적용하고, “접근성이란 무엇인지, 왜 중요한지”만 맥락으로 갖춰 두면, 다른 팀과의 대화와 이후 단계적 개선에 도움이 됩니다.

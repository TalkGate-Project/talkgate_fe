# /consult 페이지 종합 평가 (100점 만점)

평가일: 2025년 기준  
평가 대상: `/consult` 페이지의 설계, 복잡도 처리, 유지보수성, UX, 성능, 보안 등

---

## 1. 아키텍처 및 관심사 분리 (15점 만점) — **13점**

| 항목 | 설명 | 판단 |
|------|------|------|
| 레이어 분리 | 페이지 → ConsultPageContent → ChatView → 훅/UI 컴포넌트로 명확히 분리됨 | 양호 |
| Provider 역할 | ChatProvider가 소켓 연결·대화 목록·필터를 전역으로 관리하고, 페이지 로직과 분리됨 | 양호 |
| 훅 단일 책임 | useChatController, useChatUrlSync, useAiAssistantPanel 등 역할이 구분되어 있음 | 양호 |
| 컴포넌트 역할 | Left/Main/Right 사이드바, 모달, 플로팅 패널이 각각 한 가지 역할에 집중 | 양호 |
| 감점 요인 | ChatView가 10개 이상 훅을 직접 소비해 의존성이 다소 많음; useChatController가 500줄 이상으로 비대함 | -2 |

**요약:** 전반적으로 계층과 책임이 잘 나뉘어 있으나, 일부 훅/컴포넌트가 과한 책임을 지고 있어 여유 점수에서 감점.

## 2. 상태 관리 및 데이터 흐름 (15점 만점) — **12점**

| 항목 | 설명 | 판단 |
|------|------|------|
| 단일 소스 | 활성 대화방은 `activeId` 한 곳에서 관리되고, ChatProvider·useChatController·useChatUrlSync가 일관되게 사용 | 양호 |
| URL 동기화 | useChatUrlSync로 `conversationId` 쿼리와 상태 양방향 동기화, 딥링크·뒤로가기 지원 | 양호 |
| 파생 상태 | activeConversation, filteredConversations 등 useMemo로 불필요한 재계산 최소화 | 양호 |
| 감점 요인 | URL 갱신이 Next.js transition으로 한 템포 늦게 반영되는 트레이드오프가 문서화되어 있지 않음; desiredConvIdRef 등 ref 기반 동기화가 다소 난해함 | -3 |

**요약:** 상태 구조와 URL 연동은 잘 설계되었으나, 타이밍 이슈와 ref 의존 로직이 유지보수 시 부담이 될 수 있음.

## 실전 우선순위 (이미 운영 중인 서비스 기준)

100점을 노리지 않아도, **리스크는 작으면서 점수/품질에 도움이 되는 것**과 **안 하면 나중에 문제가 되는 것**만 구분해 둠.

### 1. 리스크 거의 없이 먼저 할 것 (우선도 높음)

| 작업 | 기대 효과 | 리스크 | 비고 |
|------|-----------|--------|------|
| **ConsultFallback에 "로딩 중" 표시** | UX·인지적 완성도 상승 | 없음 | 빈 박스 대신 스피너 또는 짧은 문구만 추가 |
| **useChatUrlSync / URL 동기화 동작 주석 또는 짧은 문서** | 유지보수성·온보딩 개선, 점수 2번 항목 일부 회복 | 없음 | "URL은 Next.js transition 때문에 한 템포 늦게 반영됨" 등만 명시해도 유용 |
| **채팅 리스트·메인 영역에 aria-label 추가** | 접근성 점수 상승, 스크린 리더 대응 | 거의 없음 | 예: 상담 목록 영역, 선택된 대화방, 메시지 영역 등에만 적용 |

→ 코드 동작은 그대로 두고, **UI/문서/접근성**만 살짝 보강하는 수준이라 배포 리스크가 거의 없음.

### 2. 시한폭탄 성격 — 리스크는 있지만 해두는 게 좋은 것

| 작업 | 왜 시한폭탄인가 | 권장 방식 |
|------|-----------------|-----------|
| **/consult 구간 Error Boundary** | 렌더 중 예외(서드파티·훅 버그) 시 전체 페이지가 흰 화면. 이미 한 번이라도 나왔다면 재현만 안 될 뿐 또 날 수 있음 | consult 페이지 또는 ChatView를 감싸는 Boundary 하나만 두고, fallback에서 "일시적 오류" + 새로고침 유도. 기존 동작은 건드리지 않음 |
| **소켓 끊김 시 사용자 안내** | 연결이 끊긴 줄 모르고 메시지를 보냈다고 생각할 수 있음. 고객 문의·신뢰도 이슈로 이어질 수 있음 | `socketError` 또는 disconnect 이벤트 시 상단에 작은 배너/토스트로 "연결이 끊겼습니다. 재연결 중입니다." 정도만 표시. 재연결은 기존 Socket.IO 기본 동작 활용 |
| **핵심 플로우 최소 테스트 1~2개** | 리팩터·패키지 업그레이드 시 "원래 되던 게 깨졌는지" 모름. 회귀를 나중에야 고객이 알려주는 상황 가능 | E2E 1개 예: "상담 페이지 진입 → 대화방 클릭 → URL에 conversationId 반영" 또는 useChatUrlSync 핵심 분기만 단위 테스트. 범위는 최소한으로 |

→ **동작 변경을 최소화**하고, "실패했을 때 보여줄 것"과 "변경 시 검증할 수단"만 추가하는 쪽이 안전함.

### 3. 당장 안 해도 되는 것 (여유 있을 때)

- 메시지/대화 목록 **가상화**: 메시지 수가 수백~수천 단위로 많아질 때만 검토. 도입 시 스크롤/포커스 버그 가능성 있음.
- **useChatController / ChatView 분리**: 리팩터 자체가 회귀 리스크를 만듦. 새 기능이나 버그 수정 시 같이 조금씩 나누는 식이 안전.
- **접근성 전면 개선**(키보드만으로 모든 동작): 작업량 대비 점수 상승이 크지 않고, 우선은 aria-label 등으로 일부만 해도 충분.

---

**요약:**  
- **바로 하기 좋은 것:** 로딩 문구, URL 동기화 주석/문서, aria-label 소폭 추가 → 리스크 거의 없이 78점대에서 80점대 초반까지 끌어올리기 적합.  
- **꼭 해두는 게 좋은 것:** Error Boundary, 소켓 끊김 안내, 최소 테스트 → 한 번만 제대로 해두면 이후 장애·회귀 대응이 훨씬 수월해짐.
